# Requirements

## 1. Project goal

CertGate verifies device identity with X.509 certificates on an untrusted network and forwards only authenticated and authorized requests to an internal service.

This is not a reproduction of a specific commercial product. It reinterprets the question, "How can a server trust a network device?", in a general network-device management environment using PKI and mTLS.

## 2. Actors

- **Device Agent**: owns a private key and certificate, connects to the gateway, and sends telemetry or heartbeat requests.
- **Administrator**: registers devices, approves certificate requests, assigns roles, revokes certificates, and reviews security events.
- **Backend Service**: receives only requests approved by the gateway.

## 3. Primary scenario

1. The administrator registers a device.
2. The device generates its private key and CSR.
3. The administrator approves the CSR in the management console.
4. The private CA signs and issues the device certificate.
5. The device connects to the gateway using mTLS.
6. The gateway validates the certificate, device status, and access policy.
7. The gateway forwards only permitted requests.
8. CertGate records the decision as a security event.

## 4. Functional requirements

- **FR-01**: Administrators can register and view devices.
- **FR-02**: Devices generate private keys and CSRs; administrators can approve or reject CSRs and download issued certificates.
- **FR-03**: Devices connect to the gateway using TLS 1.3 and mTLS.
- **FR-04**: The gateway validates the issuing CA, validity period, and registered device identity.
- **FR-05**: The gateway evaluates a device role and method/path access policy.
- **FR-06**: Only permitted requests are forwarded to the backend service.
- **FR-07**: Authentication failures and access decisions are recorded as security events.
- **FR-08**: Administrators can revoke an issued certificate.
- **FR-09**: A revoked certificate cannot access the backend service.
- **FR-10**: The console displays devices, certificate requests, certificates, and security events.

## 5. Non-functional requirements

- Private keys must not be generated by or stored in the management server.
- CA private material must be mounted at runtime and excluded from Git.
- A fresh environment must be reproducible with documented commands.
- Critical allow/deny scenarios must have automated tests.
- Logs must not expose private keys, secrets, or complete sensitive payloads.
- The initial target is a portfolio-grade single-node system, not production-grade HA.

## 6. Out of scope for the submission MVP

- Full SCMS or V2X protocol implementation
- CRL distribution point or OCSP responder
- DTLS, VPN, and IPSec
- HSM/KMS integration
- Multi-tenant administration and console authentication
- High availability and automatic certificate renewal
